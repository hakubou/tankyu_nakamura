## 2. システム全体の構成

```
[QUBE振子モジュール]
  └ エンコーダ E8T-512（5V, A相/B相）
      └ 3.5mm 4極プラグ
          └ 4極ジャック（ユニバーサル基板に実装、8/19完成）
              └ NUCLEO-G474RE（★D7=A相 / D8=B相 / 5V / GND）※8/21にA相をD9→D7へ変更
                  └ USB(Micro-B) 仮想COM 921600baud → PC
                     13バイトフレームを1kHzで送信

[DM-J4310-2EC モータ]
  └ CAN → USB-CANアダプタ → PC（C#制御プログラム）
  └ 出力フランジ → 3Dプリントアダプタ → QUBE振子モジュール

           ↓ 両系統ともPCの同じプログラムに入る（8/21に接続完了）
      PendulumTelemetry（C#）で受信 → オブザーバ → LQR計算
```

**PCには USB が2本挿さる。必ず同じPCであること**（LQR計算に振子角とアーム角の両方が同時に要るため）。
- USB Micro-B → Nucleo（振子角、PCへの一方向、1kHz）
- USB → USB-CANアダプタ → モータ（トルク指令とアーム角・角速度、往復）

**アーム角はモータ自身のCANフィードバックから取る。**エンコーダをマイコンに繋いだのは振子角用のみ。
状態量4つの内訳：θ・θ̇＝モータのCANフィードバック／α＝エンコーダ経由／α̇＝オブザーバが推定。

**注意：2本のUSBが同じPCに入ることで、モータ側とエンコーダ側のGNDがPC経由で繋がる**（グランドループ）。
モータのノイズがここを通る可能性があるため、**エンコーダのケーブルとモータの電源ケーブルを平行に束ねないこと**。

| 項目 | 値 |

| 制御モード | MITモードに設定済み（フラッシュ保存済み、電源再投入後も維持） |

#### ★重要：5Vトレラントなピンとそうでないピン

データシート **DS12288 Rev 6 の Table 12（pin definition）の「I/O structure」列**で判定する。

| ピン | I/O structure | 5V直結 |
|---|---|---|
| PA3〜PA7、PB0〜PB2、PC5 など**ADC入力を持つピン** | `TT_a` | **不可（3.3Vのみ）** |
| **PC6・PC7** | `FT_f` | **可** |
| **PA8** | `FT_a` | 可 |
| **PA9** | `FT_fda` | 可（ただしUCPDのデッドバッテリー用プルダウンが起動時に有効。"d"がその印） |

#### ★ピンの物理的な並び（8/21に2回挿し間違えた）

`D0〜D7` は **CN9**、`D8〜D15` は **CN5** という別のヘッダだが、基板上は端と端が繋がって
**1本の連続した並びに見える**。境目は見た目では分からない。

```
… D5 - D6 - D7 | D8 - D9 - D10 …
              ↑CN9とCN5の境目
```

**D7 と D8 は隣同士。D9 はそこからもう1つ先。**
「D9→D7に移す」場合、**D8を1つ飛び越える**必要がある。ここを間違えてA相をD8に挿すと、
B相と同じピンを取り合う形になり、カウントが動かない（実際に起きた）。

#### エンコーダモードで使えるピンの組（5Vトレラント必須）

| タイマ | CH1 | CH2 | ビット幅 | 備考 |
|---|---|---|---|---|
| **TIM1** | **PA8 (D7)** | **PA9 (D8)** | 16bit | **★採用。両方Arduinoヘッダ上で扱いやすい** |
| TIM3 / TIM8 | PC6 | PC7 (D9) | 16bit | PC6の場所が未特定 |
| TIM2 / TIM5 | PA15 など | PB3 (D3) など | **32bit** | 5Vトレラントか未確認。PA15はMorpho側 |

**16bitでも問題ない。** 1kHzでサンプリングして**16bitの差分を`int16_t`にキャストして積算**すれば、
ラップは自然に吸収される（1msの間に16回転しない限り厳密）。オーバーフロー割り込みは不要。

#### `SignCalibration` の使い方（8/24作成）

```

dotnet run --project src/SignCalibration -- --watch-theta COM5   θ監視のみ（トルクを送らない）
```

- **測定1（s_theta）**：t_ff=+0.2N·m を300ms。モータ報告位置が増える向きでs_thetaを決める。**モジュールがアームに固定されていなくても実行できる**

#### ★Motor クラスの使い分け（8/21に学んだ重要な点）

| メソッド | 所要時間 | 用途 |
|---|---|---|
| `ReadStatus(tries)` | **1回で最大100ms超** | 起動時の疎通確認だけに使う。**定周期ループでは絶対に使わない** |
| `TorqueCommand(0.0)` ＋ `ReadFeedback(timeout)` | 数ms | **定周期ループはこちら。**「送信→即座に読む」を1組にする |

`ReadStatus()` は「一旦失能させて応答を待つ」実装のため重い。
これで回すと更新レートが**9〜19Hz**しか出ず、300Hz前提のオブザーバゲインでは即発散する。
`TorqueCommand(0.0)`＋`ReadFeedback()` に変えて**128Hz前後**まで改善した。

**トルク0ならモータは動かない。** CLAUDE.mdの「kp=0, kd=0, t_ff=0 なら指令トルクが0なので
動かないのは当然の挙動」がこれ。8/6の逆駆動テストでも寄生トルクなしを確認済み。

### 8/12：判断の誤りを特定、倒立振子で続行が決定
先生から「クーロン摩擦は補償が簡単なのでそんなに影響ないですよ」との助言。メンバーBが前提から検証をやり直し、**4件の判断の誤り**を特定した。

1. **「摩擦が必要トルクの10倍だからアーム延長300mmが必須」→ 誤り**
   比べるべきは「必要な定常トルク 対 摩擦」ではなく「**使えるトルク 対 摩擦**」。モータは2.0 N·m出せるので、摩擦は越えられない壁ではなく打ち消すべき外乱。
   さらに、素の寸法で転倒した最初のシミュレーションは**改造後のプラント用に調整したゲインを流用した不公平な比較**で、対照実験（摩擦ゼロ）でも0.04秒で転倒していた。
   → **アーム延長ブラケット（215mm）、錘（150g）、アルミ加工はすべて不要になった**
2. **「摩擦補償は必須」→ 必須ではない**
   Karnoppモデル（真の固着あり）では補償なしでも成立（1.69°）。固着ありの方がリミットサイクルが小さい（0.41° 対 0.96°）。静止摩擦は「その場に留める」問題では味方に回る。ただし前滑り変位は表現しきれないため、補償は入れる方針は維持。
3. **「スリップリングが必要」→ 不要**
   エンコーダのケーブルはブロック側から出ており、回転するのは銀の丸棒。サービスループ（たるみ）で足りる。
4. **「取り付け平面を下に伏せて板に載せる」→ 不可能**
   取り付け平面は円筒に3.5mm掘り込まれた窪みで、円筒面の方が外側に出ている。→ 円筒面で受け、M4で締結する構成に変更。

#### ★★ ここで踏んだ3つの罠（同じところで詰まらないために）★★

**罠1：`ReadStatus()` は定周期ループに使ってはいけない**

`Motor.ReadStatus()` は「一旦失能させて応答を待つ」実装で、**1回あたり最大100ms超**かかる。
これで回すと更新レートが**9〜19Hz**しか出ず、300Hz前提のオブザーバゲインでは即発散した。

→ 対処：`Enable()` してから **`TorqueCommand(0.0)` を送って即 `ReadFeedback()` で読む**方式に変更。
**128Hz前後**まで改善した。トルク0なのでモータは動かない（8/6の逆駆動テストで寄生トルクなしを確認済み）。
CLAUDE.mdの「kp=0, kd=0, t_ff=0 なら動かないのは当然の挙動」がまさにこれ。

**罠2：送っていないトルクを「送ったつもり」で予測すると発散する**

オブザーバの予測式 `x̂ ← x̂ + dt·(A·x̂ + B·u + L·(y − C·x̂))` の `u` に、
**計算しただけで実際には送っていない u_cmd** を入れていた。
モデルは起きていない動きを予測し、実測とのズレが次のu_cmdをさらに大きくし……という正のフィードバックで指数発散。

→ 対処：`Step()` に `appliedTorqueNm` 引数を追加し、**実際に送った値（＝常に0）**を渡すようにした。
**「計算はするが送らない」プレビューは閉ループ制御とは別物**、という理解が要る。

**罠3：平均レートが足りていても、まれな遅延で発散する**

罠2を直しても、まだゆっくり発散した。`A − L·C` の固有値を実際に計算したところ：

```
    -79.271 ± 78.292j     (|λ| ≈ 111)
     -8.026 ±  3.699j
```

前進オイラー法が数値的に安定なのは**おおよそ dt < 13ms**。平均128Hz（7.8ms）は満たしていたが、
**CAN応答がまれに遅れて13msを超えた瞬間だけ誤差が数倍に膨れ、それが蓄積して爆発**していた。
平均値だけ見ていては気づけない種類の不安定さ。

→ 対処：`FurutaObserver.Step()` 内で、**dtが大きいときは2ms以下に分割して複数回積分する**（測定値はその間一定＝零次ホールド）。これで安定した。

### ★★★スイングアップ（振り上げ→キャッチ）の実装と成功

「維持」の頑健性確認が済んだあと、メンバーAの判断で同日中にスイングアップへ着手した。

#### 方式：エネルギー整形則

`model/furuta_model.py`と同じLagrangianの枠組みで、振子の力学的エネルギー
E(α,α̇) = ½·J_pivot·α̇² + m_p·g·l_p·cosα （J_pivot = J_p + m_p·l_p²、支点まわり）
を導出し、dE/dt = −m_p·l_p·a·α̇·cosα（aはアームの接線加速度）という関係から、
**a = k_e·(E−E_top)·sign(α̇·cosα)** とすればエネルギーが単調に増えることを導いた（メンバーAが手計算、詳細は`src/SwingUp/Program.cs`冒頭のコメントに導出込みで記録）。実装ではa→トルクの厳密な変換はせず、`SwingGain·(E−E_top)·sign(...)`を直接トルク指令として使う経験的な形にした。

#### 開始条件：振子が真下で静止するのを自動検出

メンバーAの指摘（8/26、維持の議論中）を反映し、**「真上に持っていってEnter」ではなく、振子が自然に真下で静止するのを自動検出してから校正する**方式にした。1秒間の振れ幅が2°未満になったら静止と判定。人間の手癖による初期条件のばらつきが無くなった。

#### つまずいた点1：アームの「押しっぱなし」による暴走（40°→即座に安全ガード）

初回試行、振り上げ開始0.4秒でアーム角±140°の安全ガードに到達。**エネルギー整形則は振子だけを見ており、アーム自身には位置を戻す力が一切無かった。** 振子が真下から水平に近づくまでの約1/4周期の間、力の向きが変わらず、軽いアーム（J_r=0.00213）が加速度的に振り切れた。

- 1回目の対処（常時弱いバネKp=1.0）→ 暴走は止まったが、今度は**振子の振れ幅が11.6秒間まったく育たなくなった**。バネがエネルギー整形則のポンピング動作自体を打ち消していたと判断
- 2回目の対処（**閾値方式**）：±30°以内は常時ごく弱い減衰のみ、それを超えた分にだけ強いバネ（Kp=5.0）を掛ける方式に変更 → **振子の振れ幅が正常に育ち、約5.8秒で上向き付近（キャッチ角度±25°以内）に到達**

#### つまずいた点2：キャッチ切り替え直後の飽和トルクによる再暴走

振り上げ自体が成功した初回、キャッチに切り替えた瞬間に`u_total`がいきなり−2.00（飽和）になり、0.3秒でアーム角±140°の安全ガードに到達して失敗した。

**原因：振り上げ中に使っていた「巻き戻さないα」をそのままLQRのオブザーバに渡していた。** 振り上げでは振子が何周も振れるため、内部的なα（生の値）は数百度分蓄積している。表示上の角度（±180°に巻き戻した値）は+23.9°でも、オブザーバに渡していた生の値はそれとかけ離れた大きな数値になっており、LQRが「αが激しくズレている」と誤認して即座に飽和トルクを出していた。

**対処：キャッチフェーズでオブザーバに渡す直前だけ、±180°に巻き戻した値に変換する**（`alphaWrapped * π/180`）。振り上げフェーズ自体の物理計算（cos/sinを使うため巻き戻し不要）はそのまま。

`CatchAlphaDotMaxRadPerSec = 3.0`（LQR設計のBryson α̇許容偏差に合わせた）。

**きっかけ**：振り上げ1.1秒 → キャッチ0.1秒後に振子角ガード、という試行が出た。**角度しか見ていないため、高速で真上を通過する瞬間に切り替わってしまい、LQRの最大トルクでは止めきれていなかった。**

**安全性の根拠**：エネルギー整形則は E>E_top だと dE/dt<0 になり、自動的にエネルギーを削る側に働く。**切り替えを見送っても暴走せず、法則自身が減速して次の通過を待てる。**

**効果：成功率が55%→89%に改善。**

| 180°（真下） | −0.0270 J | 0.405 N·m | 0.810 N·m |

### 参考：8/14に動かした最初のスケッチ（変化検知のみ）

Arduino IDEで動作確認済み。**ハードウェアのタイマ機能ではなく、割り込みでソフト的に変化を検知する簡易版**。角度のカウントはまだしておらず、「変化があったらLEDを反転する」だけ。

```cpp
const int pinA = PC7;    // D9（A相）
const int pinB = PA9;    // D8（B相）
const int ledPin = PA5;  // 基板上の緑LED（LD2）

volatile bool changed = false;

void onChange() {
  changed = true;
}

void setup() {
  pinMode(pinA, INPUT);
  pinMode(pinB, INPUT);
  pinMode(ledPin, OUTPUT);
  attachInterrupt(digitalPinToInterrupt(pinA), onChange, CHANGE);
  attachInterrupt(digitalPinToInterrupt(pinB), onChange, CHANGE);
}

void loop() {
  if (changed) {
    changed = false;
    digitalWrite(ledPin, !digitalRead(ledPin));  // 変化があるたびLEDを反転
  }
}
```

### ★現在の配線（8/21のTIM1移行後）

| 先端（5V） | 赤 | 赤 | `5V`ピン |
| リング1（**A相**） | 白 | 白 | **`D7`（PA8＝TIM1_CH1）** |
| リング2（**B相**） | 緑 | 緑 | **`D8`（PA9＝TIM1_CH2）** |

### 動作確認時に見られた正常な挙動（次回迷わないためのメモ）

- **ジャンパーを挿した瞬間にLEDが反応する**：ピンが「宙ぶらりん（フローティング）」から「はっきりした電圧」に変わるのも1回の変化として検知されるため、正常
- **繋いだあと放置すると点きっぱなし**：変化がなければ状態を保つ仕様なので正常。点灯/消灯そのものに意味はなく、「変化が起きるか」だけを見る

- **回すのをやめるとちらつきが止まる** ← これが成功の判定基準

### エンコーダの検証手順（8/19・8/21ともこの4項目で確認した）

`textMode = true` で書き込み、**シリアルモニタを921600 baud**にして：

1. **ゆっくり1回転** → **2048前後**か（1024なら2逓倍になっている、512なら1逓倍）
2. **高速で5回転** → 理論値10240との差が小さいか（8/21のTIM版は差3カウント）
3. **元の位置に戻す** → 開始値付近に戻るか（戻らなければ取りこぼし）
4. **符号の向き** → 先端から見て時計回りで増えるか。**逆ならA相B相のジャンパを入れ替える**（ソフトで直すより確実）
5. **静止させて放置** → 数値が動かないか（ドリフト確認）

**実測比較**

|---|---|---|
| 1回転 | ほぼ2048 | **2048（誤差0）** |
| 高速5回転の誤差 | 10カウント | **3カウント** |
| モータ稼働時のノイズ | **未検証** | **誤カウントなし（実測）** |

### なぜ有用か

このオシロスコープアプリは「**マイコンで測った値をシリアル通信でPCに送り、PC側でリアルタイムにグラフ表示する**」もので、**振子の角度をPCに送って表示する部分にそのまま流用できる**。

資料3の付録にあるマイコン側の通信プロトコルは以下の通り（すでに読み取り済み）。

- `#define USBCON` / `#define USBD_USE_CDC` … USB CDC（仮想COMポート）を使う
- `Serial.begin(115200)`
- `analogReadResolution(12)` / `analogWriteResolution(12)` … ADC/DACは12bit
- **送信（マイコン→PC）8バイト**：`0xAF, 0x55`（ヘッダ）＋データ5バイト＋**XORチェックサム1バイト**
- **受信（PC→マイコン）**：同じく`0xAF, 0x55`をヘッダとして待ち受け、XORで検証
- `loop()`は「PCから受信 → DAC出力 → ADC読み取り → PCへ送信 → `delay(1)`」の繰り返し

同じ枠組みで、ADCの値の代わりに**エンコーダのカウント値**を送れば、そのままPC側で角度が見られるようになる。

### 制御調整時の注意（メンバーBの検証より）

**ゲイン感度が高い。** 許容トルク（Brysonの重み）を0.01→0.02に変えるだけで、リミットサイクルが0.24°→5.37°と20倍以上悪化する（非単調）。スイートスポットは0.005〜0.01 N·m付近。**実機ではシミュレーションの最適点が最適とは限らないので、対数的に振って探す前提でいること。**

**★8/26追記：この感度の高さは実機でも別の形で確認した。** `FurutaObserver.Step()`にK[0]（θの復元力）だけを個別に手で3倍する引数を追加して試したところ、かえって悪化（発散が速くなった）。**Kは常に`design_and_simulate.py`のBrysonの重み経由で4要素まとめて再設計すること。個々の要素を手で弾ませてはいけない。** 詳細は§4の8/26。

**オブザーバの観測雑音は量子化誤差だけで見積もらないこと（8/17）。** 実機ではタイミングジッタ由来の誤差が量子化誤差の**7倍**あった。これを入れずに慣性を実測値へ更新したところ、シミュレーションが全ケース転倒した。**マイコン側で角度を送る実装をするときも、送信周期のジッタがそのまま制御性能に効いてくる**ので、タイマ割り込みで等間隔に送る／タイムスタンプを一緒に送る、といった配慮が要る。

**モータへの角度指令は「モータ内部の絶対角」で出さないこと（8/17）。** 加振ツールがこれをやっていて、実機に143°の引き戻し指令が出るところだった。**起動時の実測位置を基準にした相対角**で指令し、開始角から一定以上ずれたら打ち切るガードを必ず入れる。

## 11. 作業環境の注意点（同じところで詰まらないために）

### ST公式サイト（st.com）は自動アクセスをブロックする

`curl`もWebFetchも接続がタイムアウトする。データシートやユーザーマニュアルが必要なときは、**ブラウザで手動ダウンロードしてフォルダに置いてもらう**必要がある。
（8/14の`STM32G474RE　データシート.pdf`はこの方法で共有してもらった）

代替として、GitHubのAPIは使える。STM32duinoのボード定義ファイル（ピン番号の対応表）はGitHubから直接取得できた。

### 日本語PDFの読み方

poppler系のツール（`pdftoppm` / `pdftocairo` / `pdftotext`）は、日本語のCIDフォントを使ったPDFで
`Missing language pack for 'Adobe-Japan1' mapping` というエラーを出し、**日本語が消えた画像を出力してしまう**。
デザイン実習資料がまさにこれだった。

代わりに**PyMuPDF**を使う。導入済み（pymupdf 1.28.0）。

```bash
python -X utf8 -c "
import fitz
doc = fitz.open(r'C:\path\to\file.pdf')
print(doc[0].get_text())
"
```

**注意**：Pythonに渡すパスは`C:\...`のWindows形式にすること。Git Bashの`/c/...`形式はPythonが解釈できず`FileNotFoundError`になる。また`-X utf8`を付けないと日本語パスが文字化けする。

一部のPDF（Damiaoのマニュアル等）はReadツールが「password-protected」と誤判定することがある。その場合はページを画像に変換してから読む。

### STM32CubeIDEで詰まった経緯（参考）

Arduino IDEに切り替える前、CubeIDEで以下の問題に遭遇した。もし将来また使うことになったら注意。

- インストールしたバージョン（2.2.0）では、`File → New`メニューに「STM32 Project」が無く、`New → Other... → STM32CubeIDE Empty Project`から入って**「Next」を1回押した先**にボード選択画面（Board Selector）があった
- 「Empty Project」で作ると`stm32g4xx.h`などのチップ定義ファイルが含まれず、`fatal error: stm32g4xx.h: No such file or directory`でビルドできない。レジスタのアドレスを直接`#define`すれば回避できるが、そもそもピン設定ツール（CubeMX）の画面に辿り着けなかった
- スタンドアロンの STM32CubeMX は同梱されていなかった

### ★シリアルポートは同時に1つのプログラムしか開けない（8/21に2回詰まった）

`Access to the path 'COM4' is denied.` が出たら、**Arduino IDEのシリアルモニタが開きっぱなし**を疑う。

- シリアルモニタを閉じてから `dotnet run` する
- 逆も同じ。C#を動かしたままシリアルモニタは開けない

### ★.NET SDK の導入（8/21に時間を溶かした）

**先に `dotnet --list-sdks` で既存インストールを確認すること。**

- このPCには `C:\Program Files\dotnet` に**SDKなしの壊れたインストール**が既にあった
- **Windowsはシステム側PATHをユーザー側PATHより先に検索する**ため、
  ユーザー領域(`%USERPROFILE%\.dotnet`)に入れても壊れた方が優先されて隠れてしまう
- 正解は**管理者権限で `C:\Program Files\dotnet` に入れ直す**こと
- インストールは `https://dot.net/v1/dotnet-install.ps1` を使った（Microsoft公式）
- **UACの確認画面はメンバーA本人の操作が必要**（自動化ツールからは押せない）。
  スクリプトファイルに書き出してから `Start-Process powershell -Verb RunAs -File` で起動すると通った
  （複雑な引用符を `-Command` に渡す方法では失敗した）

**現在の状態：`C:\Program Files\dotnet` に SDK 10.0.400。どのウィンドウでも `dotnet` で動く。**

### ★環境変数PATHの変更はウィンドウの再起動では反映されないことがある

Windows Terminal は新しいタブを開いても起動時のPATHを引き継ぐ。
**アプリ自体を完全に終了して開き直す**必要がある。
それでも駄目なら、フルパス（`"%USERPROFILE%\.dotnet\dotnet.exe"`）で直接呼べば作業は進む。

### USB-シリアルの遅延設定について（8/21、先生の指摘）

- **CH340（wch.cn）にも ST-LINK VCP にも Latency Timer の項目が無かった**（先生と一緒に確認）
- デバイスマネージャー → ポートの設定 → Advanced にあるのは16550 UART互換の Receive/Transmit Buffer で、
  USB-シリアルでは効かないことが多い。**Receive Buffer は 1（最小＝低遅延）にしてある**
- レジストリ（`HKLM\SYSTEM\CurrentControlSet\Enum\<DeviceID>\Device Parameters`）にも `LatencyTimer` は無い
- **FTDI（FT232等）なら確実にある。CH340は事情が違う**
- 代わりに**コード側で `timeBeginPeriod(1)`** を入れた（§4の8/21を参照）
- **★8/21、効果を実測済み。** `PendulumTelemetry` を約40秒（総更新25,886回）走らせた結果：
  - `obs更新Hz` 平均約600Hz（設定前の128Hzを大幅に上回る）
  - 最大dt 10.5ms、**13ms超は0回（0.000%）**
  - `timeBeginPeriod(1)` が明確に効いていることを確認。この数値をWrikeの報告に使う

  - ギリシャ文字：α β γ δ θ λ μ ω π φ ψ Σ Δ ∂
  - 上付き：² ³ ⁴ ⁿ ⁻¹。複雑な指数は括弧で e^(−ω²t)
  - 下付き：₀ ₁ ₂ ₘ ₙ

  - 独立した式は行を分けて書く
